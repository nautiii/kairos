# Data code — domain models, repositories, Firestore

Patterns with code: architecture skill, `references/patterns.md` §1–4; decisions D4, D5, D6, D8.

## Domain (`domain/`)

- Pure Dart: no Flutter UI, Firebase, Riverpod, plugin or `l10n` import; never reads the clock
  (`today` is a parameter).
- Models: Dart 3.13 primary constructor (`class const X({required final …})`), `copyWith`
  with `clearX` flags for nullable fields, `==`/`hashCode`; no `fromFirestore`/`toJson` — mapping
  lives in private functions of the repository. Named after the concept (`Birthday`,
  `UserProfile`, `Book`), never with a `Model` suffix.
- Form input is a draft (`XDraft`, e.g. `BirthdayDraft`) carrying its validation rule; a picked
  file becomes bytes, never an `XFile`.
- Failures: `enum XFailure implements Exception`, or a `sealed class` when cases carry data. No
  user-facing text.

## Repositories (`data/`)

- Fetch and push only: no state, no business rule, no UI string, no `BuildContext`; never call
  another feature's repository.
- SDKs come through the constructor (target: from `firestoreProvider`); no new
  `FirebaseFirestore.instance` default. `xRepositoryProvider` sits next to the class.
- Translate SDK exceptions into the feature's failures at the boundary, keeping the stack trace
  (`Error.throwWithStackTrace`).
- `snapshots()` streams are the source of truth, no second cache. Write futures resolve on server
  acknowledgement only: return them, the UI doesn't wait.
- Ids generated client-side (`collection.doc()`); timestamps from the clock, not
  `FieldValue.serverTimestamp()` (null in local snapshots until acknowledged).
- Tolerant reads (absent field → default, never `data()!`); omit null optionals on write. A new
  field keeps old documents readable and gets a repository test with an old-shape document.
- Multi-document writes in a `WriteBatch` (≤ 500 operations).
- Photos are compressed base64 inside the document (512 px, quality 80; no Firebase Storage):
  keep them small, a Firestore document is capped at 1 MiB.

## Firestore layout and rules

- New per-user collections live under `user/{uid}/<collection>`: isolation comes from the path.
- Legacy top-level `birthday` and `books` documents carry `uid`: every query filters
  `where('uid', isEqualTo: uid)` (rules are not filters — a query without it is rejected) and
  every create sets it. `category` documents are shared: any signed-in user reads and creates.
- A new collection or path changes `firestore.rules` in the same change; on update, the owner
  can't change (`request.resource.data.uid == resource.data.uid`).
- The maintainer deploys rules (`firebase deploy --only firestore:rules`): say when a change needs
  it, never deploy yourself.
- Schema changes are additive (read both shapes, write the new one). Migrating existing data is a
  system change: brief and approval.
- `lib/core/firebase_options.dart` is generated by FlutterFire, never edited by hand;
  `firebase.json` still points to `lib/firebase_options.dart`, so after `flutterfire configure`
  move the new file back to `lib/core/`.
