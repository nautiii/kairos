## 1. Target tree

```
lib/
├── main.dart                 # entry point: bindings, Firebase and plugin init, runApp(ProviderScope(App))
├── app/                      # composition root — the only code that knows every feature
│   ├── app.dart              # MaterialApp: theme, locale, l10n, home or router
│   ├── router/               # route table: path → screen, guards
│   ├── shell/                # main scaffold and tabs, composing feature screens
│   └── bootstrap/            # reactions to the app lifecycle: session start, permissions, eager providers
├── core/                     # feature-agnostic building blocks — never imports app/ or features/
│   ├── common/               # dumb shared widgets (design system, see the ux-ui skill)
│   ├── theme/  animations/   # AppTheme, tokens, AnKiColors, shared motion
│   ├── routing/              # route paths only (no screens): what features navigate with
│   ├── providers/            # infrastructure providers: Firebase instances, clock, config
│   ├── services/             # thin plugin wrappers used app-wide: notifications, biometrics, contacts
│   ├── config/  constants/  extensions/
│   └── firebase_options.dart # generated by FlutterFire
├── features/
│   └── <feature>/
│       ├── domain/           # pure Dart: models, value objects, enums, rules, failures
│       ├── data/             # repositories (+ Firestore/HTTP mapping), API clients used by this feature only
│       ├── providers/        # state and logic: data providers, controllers (Notifiers), derived providers
│       ├── screens/          # route targets (pages)
│       └── widgets/          # feature widgets, sheets, dialogs, domain → text/icon/color mappers
└── l10n/                     # ARB files (FR template + EN) and generated localizations

test/                         # mirrors lib/ file by file
├── architecture/architecture_test.dart
├── core/…
├── features/<feature>/<layer>/<file>_test.dart
└── support/                  # shared fakes and the widget harness
```

Every folder is optional until it has a file: a feature with no screen has no `screens/`. Start
flat inside a layer; group by sub-concept (`widgets/calendar/`) once a layer folder passes ~10
files.

## 2. Zones

| Zone | Owns | May import | Never imports |
|------|------|------------|---------------|
| `main.dart` | process start, plugin init, `ProviderScope` | everything | — |
| `app/` | composition: `MaterialApp`, route table, shell, lifecycle orchestration | `core/`, any feature, `l10n/` | `main.dart` |
| `core/` | what any feature could use without knowing the others | `core/`, `l10n/`, packages | `app/`, `features/` |
| `features/<f>/` | one user capability, end to end | own layers, `core/`, `l10n/` (UI only), declared features | `app/`, `main.dart` |
| `l10n/` | strings: `intl_fr.arb` (template) and `intl_en.arb`, edited by hand | — | `app_localizations*.dart` is generated by `flutter gen-l10n`, never edited |

Why a composition root: features stay unaware of each other's screens and of the app's layout, so
a feature can be added, moved into a tab, or deleted without touching its peers. Only `app/`
pays the cost of knowing everything, and it contains no business logic.

## 3. Layers inside a feature

The official Flutter architecture (MVVM: View, ViewModel, Repository, Service) mapped onto
Riverpod and folders. Arrows show allowed imports; nothing points up.

```
screens/ ─┐
widgets/ ─┴─► providers/ ──► data/ ──► domain/
     │            │            │          ▲
     └────────────┴────────────┴──────────┘   (everyone may import domain/)
```

| Layer | Role (Flutter guide name) | Contains | Must not |
|-------|---------------------------|----------|----------|
| `domain/` | domain models + business rules | immutable models, drafts (`XDraft`), enums, value objects, pure functions and extensions, failures | import Flutter UI, Firebase, Riverpod, plugins, `l10n`, other layers; read the clock |
| `data/` | Repository (+ Service when feature-only) | `XRepository` + `xRepositoryProvider`, Firestore/HTTP mapping, error translation, API clients | import widgets, `providers/`, `l10n`, theme; hold state; know another feature's repository |
| `providers/` | ViewModel / app state | data providers (`StreamProvider` per session), controllers (`AsyncNotifier`/`Notifier`), derived providers, side-effect providers | import `screens/`, `widgets/`, `l10n`, `core/common`/`theme`; take a `BuildContext` or `AppLocalizations` |
| `screens/` | View (routable) | pages: watch providers, call controller methods, navigate | import `data/` or backend SDKs; contain business rules |
| `widgets/` | View (pieces) | feature widgets, sheets, dialogs, `x_failure_text.dart`, `x_display.dart` | same as screens |

Why each boundary:
- **Pure domain**: the rules that matter (dates, ages, reminder planning, validation) are tested
  in milliseconds without Flutter or Firebase, and reused by UI and background code alike.
- **Data knows no UI**: repositories can serve a screen, a notification scheduler or a migration
  script; they translate SDK errors into domain failures so nothing above sees Firebase codes.
- **State knows no widgets or words**: providers expose typed state and failures; the UI picks the
  words with `context.l10n`. That keeps locale switches, tests and reuse trivial.
- **Widgets render**: they read providers and forward intents. A widget that decides or fetches
  is untestable without the whole stack.

## 4. Placement table

| You are writing… | Put it in | Name |
|---|---|---|
| An entity, value object or enum | `features/<f>/domain/` | `idea.dart` → `Idea` (legacy: `XModel`) |
| Form input before saving | `domain/` next to the model | `IdeaDraft`, with its validation getter |
| A business rule (dates, ages, sorting, filtering, validation) | `domain/` as a pure function or extension taking every input, `today` included | `birthday_dates.dart` |
| A failure the user can hit | `domain/<f>_failure.dart` | `enum XFailure implements Exception`, or `sealed class` when cases carry data |
| Firestore or HTTP access | `data/<x>_repository.dart` | `XRepository` + `xRepositoryProvider` in the same file |
| Firestore ↔ model mapping | private functions in the repository file; `data/<x>_mapper.dart` once it passes ~60 lines or handles schema versions | `_xFromDoc`, `_xToMap` |
| A plugin or API used by one feature | that feature's `data/` | `GoogleBooksApi` |
| A plugin used by ≥ 2 features or by `app/` | `core/services/` + provider | `NotificationService`, `notificationServiceProvider` |
| Firebase instances, clock, today's date, HTTP client, config | `core/providers/` | `firestoreProvider`, `clockProvider`, `todayProvider` |
| The current user id | `features/auth/providers/session_providers.dart` | `currentUidProvider` |
| A list or document the UI shows | `providers/` as a session-scoped `StreamProvider` | `ideasProvider`, `personIdeasProvider(id)` |
| Screen actions (save, delete, import) and their progress/error | `providers/` as a controller | `IdeaEditor` → `ideaEditorProvider` |
| Search text, filters, selected view | `providers/` as a small `Notifier<T>` | `birthdaySearchProvider` |
| A filtered, sorted or combined view of data | `providers/` derived provider calling a domain function | `filteredBirthdaysProvider` |
| A reaction to data changes (reschedule notifications) | `providers/` side-effect provider, activated by `app/bootstrap` | `reminderSyncProvider` |
| A page reachable by navigation | `screens/` + path in `core/routing/` + entry in `app/router/` | `IdeasScreen` |
| A sheet or dialog | `widgets/` with `static Future<T?> show(context)` | `AddIdeaSheet` |
| Failure → message, enum → label/icon/color | `widgets/` | `idea_failure_text.dart`, `category_display.dart` |
| A widget used by ≥ 2 features | `core/common/`, dumb (params + callbacks) | `AnKiEmptyState` |
| Orchestration across features triggered by a user action | the lowest feature that already depends on every participant (often `settings`), else a new feature (`account`) | `AccountDeletion` |
| Orchestration triggered by the app lifecycle (sign-in, start) | `app/bootstrap/` | `SessionBootstrap` |
| Tab selection, shell layout | `app/shell/` | `MainShell`, `mainTabProvider` |
| Asset paths, fixed keys | `core/constants/` | `AppAssets` |
| A fake shared by several test files | `test/support/` | `FakeIdeaRepository` |

When two rows seem to fit, choose the one lower in the dependency order (domain < data <
providers < widgets/screens; feature < core only when feature-agnostic). Code moves up easily;
moving it down later means untangling.

## 5. Dependency rules

Rule ids are the ones the architecture test prints.

| Rule | Statement | Why |
|------|-----------|-----|
| `core-isolation` | `core/` never imports `features/` or `app/` | core is reusable by every feature; one feature import makes it depend on all |
| `app-only` | only `main.dart` imports `app/` | composition stays at the top; no feature knows the app layout |
| `feature-graph` | a feature imports another only along a declared, acyclic edge | cycles make features impossible to change, test or delete alone |
| `screens-private` | no feature imports another feature's `screens/` | navigation goes through paths, so screens can move, nest or become routes freely |
| `repositories-isolated` | a `data/` file never imports another feature's `data/` | repositories don't know each other (Flutter guide); combine sources in providers |
| `domain-purity` | `domain/` imports only `dart:` core libraries, `flutter/foundation.dart`, `meta`, `collection` and other `domain/` folders | pure, fast, reusable rules |
| `data-no-ui` | `data/` imports no widgets, `providers/`, theme or `l10n` | data serves every caller, UI or not |
| `state-no-ui` | `providers/` imports no `screens/`, `widgets/`, `l10n` or core UI | state is UI-agnostic; the UI chooses words |
| `ui-no-backend` | `screens/` and `widgets/` import no `data/` and no backend SDK | widgets render state; I/O goes through providers |
| `layout` | every feature file sits in one of the five layers | the structure stays predictable for humans and agents |

What the test cannot see, review must catch: `ref.read(xRepositoryProvider)` inside a widget,
business rules in a `build` method, `DateTime.now()` in domain code, a repository holding state,
strings built in a provider.

## 6. The feature graph and how to break cycles

The graph is declared in `featureDependencies` (architecture test). `app/` may import every
feature and is not part of it.

| Feature | May import — today | May import — target (`migration.md`, planned bricks) |
|---------|--------------------|------------------------------------------------------|
| `auth` | — | — |
| `user` | auth | auth |
| `birthday` | auth, user | auth, user |
| `book_scanner` | auth, user | absorbed by `ideas` |
| `home` | birthday, book_scanner | moved to `app/shell` |
| `reminders` | | auth, birthday |
| `ideas` | | auth, birthday |
| `settings` | | auth, user, birthday, reminders |
| `onboarding` | | auth, birthday, reminders |

Reading the target: `auth` and `user` are foundations, `birthday` (people and their dates) is the
core domain, everything else builds on it, and nothing builds on `settings` or `onboarding`.

Adding an edge: the target must already be lower in the graph (no cycle), and the edge must be
about using the other feature (its domain types, providers, widgets), not about reaching into
its internals. Say so in the brief; declare it in the same change.

When an import would create a cycle, in this order:
1. **Orchestrate lower.** Move the flow to the feature that already depends on both (or to
   `app/bootstrap` when the app lifecycle triggers it). Example: account deletion touches auth,
   user and birthday → it lives in `settings`, which depends on all three.
2. **React instead of calling.** The lower feature exposes state; the higher one watches or
   listens to it. Example: `user` creates the profile when `currentUidProvider` turns non-null,
   instead of the sign-up screen calling `user`.
3. **Compose with a slot.** The lower feature's widget takes a `Widget` or builder parameter;
   `app/router` passes the other feature's widget. Example: the person page (birthday) shows a
   gift-ideas section built by `ideas`, wired in the route builder.
4. **Move the shared concept down.** A type both need goes to the lower feature's `domain/`, or
   to `core/` if it is truly feature-agnostic (like `BirthdayReminder` in `core/services`).

## 7. Naming

- Files `snake_case.dart`, one public concept per file (a model and its draft may share one).
- Domain types are named after the concept (`Idea`, `ReminderPlan`, `UserProfile`). The `Model`
  suffix (`BirthdayModel`, `UserModel`, `BookModel`) is legacy: keep it while those types live
  on, don't add new ones. Avoid names that clash with SDK types (`User`, `Category`).
- Repository `XRepository` / `xRepositoryProvider`; service `XService` / `xServiceProvider`.
- Data providers are nouns: `birthdaysProvider`, `personIdeasProvider(personId)`.
- Notifiers are named by role: `IdeaEditor` (writes), `BirthdaySearch` (UI state); the
  provider is the lowerCamel name + `Provider`. Existing `XNotifier` names stay until touched.
- `XState` only when a Notifier holds several fields that change together; prefer `AsyncValue`.
- Screens `XScreen`, sheets `XSheet`, tiles `XTile`, failures `XFailure`, drafts `XDraft`
  (legacy: `CreateXInput`).
- Tests: `<file>_test.dart` mirroring the path; a flow across several screens of a feature:
  `test/features/<f>/<flow>_flow_test.dart`.

## 8. Growing: split, promote, extract

| Signal | Move |
|--------|------|
| A feature has two independent reasons to change, or passes ~25 files | split it (e.g. `groups` out of `birthday`) and declare the edge |
| A layer folder passes ~10 files | sub-folders by concept inside the layer |
| A second feature needs a feature-agnostic helper or plugin wrapper | promote it to `core/` |
| A second feature needs a feature-specific model or provider | declare an edge to the owner, don't copy |
| Two apps share code, a team owns a feature, or analysis/build time hurts | extract packages (pub workspace): one per feature or per layer; the DAG becomes pubspec dependencies |

The rules above are what make the last row mechanical: a feature that respects them already has
the shape of a package.

## 9. The architecture test

- Install: copy `assets/foundation/test/architecture/architecture_test.dart` to
  `test/architecture/`. It ships with today's debt in `knownViolations`, so it starts green.
- It runs with the rest of `flutter test` (pure `dart:io`, ~1 s) and prints violations grouped
  by rule, each with its fix hint.
- Adding a feature: add it to `featureDependencies` with its edges (the test fails until you do).
- Fixing debt: the test lists the `knownViolations` lines that no longer match — delete them. The
  set only shrinks; a new violation is fixed in code, not added to the set.
- It reads `import`/`export` directives only. Generated files (`lib/l10n/`, `*.g.dart`) are skipped.
